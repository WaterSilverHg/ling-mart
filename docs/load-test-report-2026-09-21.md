# 轻营（LingMart）· 核心链路压测报告

| 项目 | 内容 |
| --- | --- |
| 日期 | 2026-09-21 |
| 脚本 | `scripts/load-test/lingmart-core.k6.js`（k6 v2.1.0） |
| 数据 | `scripts/load-test/seed/seed-loadtest.sql`：20 店 / 500 SPU / 1500 SKU / 1500 库存行 / 40 账号 |
| 环境 | 单机 Windows + Docker Desktop，全部中间件与 8 个服务本机运行（`docker-compose.yml`） |
| 负载 | 梯度 20 → 50 → 0 VU，共 50 秒（外加 30s 优雅停机），`sleep(1)`/迭代 |
| 结果 | **24/24 断言通过；0 真实失败；另有 296 次请求被限流拒绝（单独计数）** |

---

## 一、摘要

- **功能正确性**：24 条断言 100% 通过，且不只校验协议层——`detail` 返回的 `spuId` 与请求一致、
  购物车改数量后 `num` 确实变成 2、支付后订单 `payStatus=1`，说明链路真的通了，不是"接口没报错"。
- **延迟表现良好**：整体 p95 **70.4ms**；只读链路 p95 **37.1ms**，购物车 38.3ms，
  下单 111.5ms，支付 104.5ms。写链路约为读链路的 **3 倍**（Seata 全局事务 + 落库 + 事件写入）。
- **唯一的容量边界是配置**：搜索链路被 Sentinel 限制在 **50 QPS**（三处规则都是 50），
  50 VU 下平均约 39 req/s 未越界，但**突发时会瞬时越界，共 296 次请求被拒**（占 5.1%）。
  这是有意配置的自我保护，不是故障；想在这个并发下不被拒，需要调高阈值。
- **零真实错误**：5845 个请求中 0 个 5xx / 超时 / 断连。

> 说明：`http_req_failed = 0.00%` 的口径是"真实失败为 0"。被限流的 296 次请求**不计入失败率**
> （请求根本没被服务，断言它没有意义），但通过独立指标 `http_429_throttled` 完整呈现，没有被藏起来。

## 二、测试范围

每次迭代按权重随机进入一个场景（读 60% / 购物车 15% / 下单 15% / 支付 10%）：

| 场景 | 步骤 | 是否留数据 |
| --- | --- | --- |
| `read` | 商品检索（随机价格/销量排序）→ 检索店铺 → 店铺主页 → 商品详情 | 否 |
| `cart` | 上述浏览 → 加购 → 改数量 → 列表校验 → **删除** | 否（闭环） |
| `order` | 上述浏览 → 下单 → **取消** | 否（闭环） |
| `pay` | 上述浏览 → 下单 → 支付 → 查订单详情校验状态 | 是（已支付订单，见第六节） |

**24 条断言**（全部通过）：

- 检索：业务码、列表结构、有命中、商品字段完整（价格为正）、店铺列表结构与命中
- 店铺主页：业务码、返回的店铺 id 与请求一致、商品列表是数组
- 商品详情：业务码、**返回的 spuId 与请求一致**、SKU 非空且是数组、价格为正
- 购物车：加购成功、列表结构、**列表含刚加购的 SKU**、改数量成功、**改数量后 num=2 真的生效**、删除成功
- 订单：**下单成功并返回 orderSn**、取消成功、支付成功、**支付后 payStatus=1**

## 三、结果

### 3.1 延迟（毫秒）

| 链路 | avg | med | p90 | p95 | p99 | max |
| --- | --- | --- | --- | --- | --- | --- |
| 整体 | 22.53 | 14.88 | 48.35 | **70.38** | 116.83 | 1050 |
| `read` | 15.82 | 12.93 | 30.38 | 37.12 | 57.71 | 157 |
| `cart` | 17.78 | 13.94 | 30.10 | 38.32 | 63.57 | 553 |
| `order` | 43.12 | 28.96 | 91.34 | 111.49 | 158.83 | 263 |
| `pay` | 40.18 | 22.28 | 86.93 | 104.45 | 169.36 | 1050 |

门槛：整体 `p95<800ms`；`read<500ms`；`cart/order/pay<1500ms` —— **全部通过，余量充足**。

### 3.2 吞吐与规模

| 指标 | 数值 |
| --- | --- |
| 请求总数 | 5845（111.8 req/s） |
| 迭代总数 | 1288（24.6 iter/s） |
| 断言总数 | 15423（294.9/s） |
| 各场景请求数 | `read` 2882 / `cart` 1592 / `order` 688 / `pay` 662（另 21 为 setup） |
| 网络 | 接收 14 MB / 发送 2.3 MB |
| 持续时间 | 52.3s（含 10s 爬升 + 10s 回落） |

> 上面的场景请求数是**实测值**，不必（也无法）用"每轮固定请求数 × 权重"去精确反推：
> 场景权重是每轮随机抽取（读 60% / 购物车 15% / 下单 15% / 支付 10%），本身有抽样波动；
> 而且**被限流的请求会中断该轮后续步骤**（例如检索店铺被拒后，这一轮就不再走店铺主页/详情/下单），
> 只会让请求数变少，不会变多。

### 3.3 错误与限流

| 指标 | 数值 | 解读 |
| --- | --- | --- |
| 真实失败（5xx/超时/断连） | **0 / 5845** | 服务链路稳定 |
| 被限流（429） | **296**（5.66/s，占 5.1%） | 搜索链路的 50 QPS 上限，见下 |

**搜索链路的限流阈值（三处，均为 50）**：

| 文件 | 规则 | 作用点 |
| --- | --- | --- |
| `nacos-config/sentinel-gateway.json` | `search-route` = 50 | 网关路由级（客户端看到的 429 来自这里） |
| `nacos-config/sentinel-search.json` | `searchProduct` = 50 | search 服务 `@SentinelResource` |
| `nacos-config/sentinel-search.json` | `/api/search` = 50 | search 服务 URL 级 |

本次搜索请求平均约 **39 req/s**（低于 50），**但负载是突发式的**：Sentinel 用 1 秒滑动窗口，
某些秒内瞬时超过 50 即被拒，累计 296 次。这说明"平均值不越界"不等于"不会被限流"。

## 四、发现与解读

1. **写链路成本是读链路的 3 倍**：`order`/`pay` 的 p95 约 110ms，而读链路 37ms。
   下单/支付要走 Seata 全局事务（建单 + 锁库存 / 支付 + 销量累加 + Outbox 写入），
   全局锁与行锁是主要成本。**这与设计预期一致**：这个量级下不需要优化，但若并发再上一个数量级，
   瓶颈会在 Seata TC 与全局锁，而不是应用服务器。
2. **`pay` 出现一个 1050ms 的离群点**（p99 只有 169ms，说明是偶发而非普遍劣化）。
   单机环境下最可能是 Seata 全局锁争用或首次触发的冷路径。**50 秒的样本不足以定性**，
   要确认需拉长到 5~10 分钟并观察 p99 是否漂移。
3. **搜索是当前架构的显式容量边界**：三处 50 QPS 是刻意调低的（源码注释写"检索较贵"）。
   压测结果显示它工作正常（超额即拒、不拖垮服务），但**也意味着"搜索吞吐"这个指标在默认配置下测不出来**。
4. **本轮是首轮真正跑通**。第一轮压测时因脚本缺陷（把分页响应的 `data` 当数组）导致
   `browse()` 每轮提前返回、**只打了两个搜索接口**，其余链路一次都没执行；
   当时的 15.38% 失败率也全部来自搜索限流。修复后才有本报告的数据。

## 六、压测后数据校验

k6 报告只反映**接口层**；"闭环真的闭环了"要落到数据层才算验证完。`pay` 场景会留下已支付订单
（业务上已支付的订单不能取消），`cart`/`order` 场景是闭环的。

完整 6 条检查在 **`scripts/load-test/seed/verify-loadtest.sql`**（只读，一条命令跑完）：

```cmd
docker exec -i lingmart-mysql mysql -uroot -proot --default-character-set=utf8mb4 ^
  < scripts\load-test\seed\verify-loadtest.sql
```

| 检查 | 期望 |
| --- | --- |
| `check1_cart_left` | **0** —— 购物车被清空（cart 场景每轮都删除） |
| `check2_pending_left` | **0** —— 无待支付残留（order 场景每轮都取消） |
| `check3_dangling_lock` | **0** —— 无"锁了但既没扣减也没解锁"的库存任务，**最能说明没有泄漏的半成品状态** |
| `check4_outbox_status` | 只出现 `1`（已发送）；出现 0/2 说明 relay 或 MQ 有问题 |
| `check5_paid_orders` | **> 0 属正常**（pay 场景留下的已支付订单） |
| `check6_task_status` | 辅助：库存任务的状态分布（0/1/2/3 各多少单） |

清理：`cmd /c scripts\load-test\seed\teardown-loadtest.bat`（DB + ES 一起清）。

## 八、后续建议

1. **要让 50 VU 不触发限流**：把上述三处 `count` 从 50 提到 ≥150，然后
   `bash scripts/push-nacos-config.sh` 推送（改环境变量 `SENTINEL_*_QPS` **无效**，
   Nacos 有规则时会覆盖本地默认值）。
2. **补卖家侧场景**：账号与数据都已就绪，只需在脚本里增加发货/退款审核/统计三种流程。
3. **拉长压测时长**至 5~10 分钟，观察 p99 与内存是否漂移（当前 50 秒只能算冒烟级）。
4. **接入 CI**：固定 `VUS`/`DURATION`/`P95_MS`，先播种再压，否则结果不可比。
5. **异常路径专项**：库存不足、并发抢购、Seata 回滚、MQ 积压——这些才是分布式事务真正的风险面，
   当前压测覆盖不到。
